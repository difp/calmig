# Получение публикаций подписок: источники и ограничения

Проверено: 31 октября 2026. Задача — фотографии аккаунтов, на которые подписан пользователь личного аккаунта, в хронологическом порядке, без видео и рекомендаций. Ни один из изученных запросов пока не подтверждён как быстрый и полный источник именно такой выборки.

## Подтверждённое по исходному коду

1. Текущая Rust-реализация в `rust-core/src/calendar.rs` получает страницы списка подписок и затем запрашивает публикации каждого профиля отдельно. Поэтому число запросов к профилям масштабируется с количеством подписок. Это свойство текущей реализации, а не гарантия лимита Instagram. При последней проверке запрос списка подписок вернул `feedback_required`; причина отказа неизвестна.
2. [ZenGram: получение подписок](https://github.com/darktekmafia/ZenGram/blob/f3613a50f730d9b31c679368b83e08b565e6842d/backend/app/services/scraper.py#L1245) реализует запрос `/api/v1/friendships/{user_id}/following/?count=200`, получая дальнейшие страницы через `next_max_id`. Это запрос **списка аккаунтов**, не пакет публикаций. Значение 200 — запрашиваемый размер, фактический размер ответа и актуальность интерфейса не подтверждены. Ранее использовавшийся адаптер `instagram-private-api` в `AccountFollowingFeed` параметр `count` не передавал.
3. [instagram4j: пагинатор домашней ленты](https://github.com/instagram4j/instagram4j/blob/v3/web/src/main/java/com/instagram4j/web/paginators/FeedPaginator.java) отправляет GraphQL с параметрами `first`, `data` и `after`, читает `xdt_api__v1__feed__timeline__connection.edges` и `page_info.has_next_page/end_cursor`. Это свидетельство существования пакетной пагинации **домашней ленты** в данной реализации. Параметры именно режима Following, хронологический порядок и полнота не установлены; подставлять этот запрос в CalmIG нельзя без проверки.
4. [Zeeschuimer: обработчик Instagram](https://github.com/digitalmethodsinitiative/zeeschuimer/blob/master/modules/instagram.js) обрабатывает ту же структуру домашней ленты и отдельно распознаёт рекомендации внутри `explore_story`; [Nora: фильтр ответов](https://github.com/nonbili/Nora/blob/main/content/services/instagram.ts) удаляет узлы рекламы. Следовательно, наличие `timeline` или только сортировка по датам сами по себе не доказывают, что в ответе исключительно подписки.
5. [InstaSane](https://github.com/n3d1117/InstaSane/blob/main/Tweak.xm) переключает нативное iOS-приложение на режим `following` и использует `paginationSource = "following"`. Код не задаёт и не документирует пригодный для этого проекта формат HTTP-запроса. [Cattoclick](https://github.com/squabbled/cattoclick/blob/9cc7fa9dae24d2eb2459ebba1f51e4dd70c3c573/cattoclick.js) лишь перенаправляет браузер на `/?variant=following`, не реализуя API пагинации.

## Официальный API Meta

Документация Meta для [Instagram API с Instagram Login](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/) описывает API для профессиональных аккаунтов (компаний и авторов) и перечисляет публикацию и получение их медиа, модерацию комментариев и обмен сообщениями с клиентами. Для личного аккаунта пользователя этот вариант не заявлен; пакетная хронологическая выдача публикаций подписок в перечисленных возможностях также не указана.

Для [Instagram API с Facebook Login](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-facebook-login/) Meta прямо указывает, что API не имеет доступа к потребительским аккаунтам (не компаниям и не авторам), а сортировка результатов не поддерживается. Доступ к данным других аккаунтов в описанной функции Business Discovery касается профессиональных аккаунтов. Следовательно, этот вариант не соответствует требованию сохранить личный аккаунт и получать фотографии всех подписок. По [индексу документации](https://developers.facebook.com/documentation/instagram-platform/llms.txt) и просмотренным страницам подходящий официальный метод не найден; это не доказательство отсутствия любого недокументированного интерфейса.

## Практический вывод и проверка

Instagram в [объявлении режима Following](https://about.instagram.com/blog/announcements/favorites-and-following) от 2022 года описывает его как публикации аккаунтов, на которые подписан пользователь, в хронологическом порядке. Это описание пользовательского интерфейса, а не спецификация API или гарантия полноты и нынешнего поведения. Оно само по себе не позволяет безопасно определить формат данных для CalmIG.

Самый перспективный кандидат — пакетная выдача Instagram в режиме Following, а не обход каждого профиля. В ходе локальной проверки авторизованного Firefox первая и следующая страницы режима `/?variant=following` ответили HTTP 200. Наблюдалась операция `PolarisFeedRootPaginationCachedQuery_subscribe`: в параметрах `variant` и `data.pagination_source` были равны `following`, а для пагинации использовался `after`. В ответе присутствовали `edges.node.media`, `page_info.has_next_page` и курсор. Это наблюдение конкретной версии неофициального интерфейса, а не стабильная спецификация.

В последующей проверке с одной браузерной сессией мобильный запрос CalmIG к списку подписок вернул `feedback_required`, тогда как браузерный Following загрузился. Первый экспериментальный Rust-запрос к веб-операции вернул HTTP 200 с четырьмя ошибками GraphQL и без данных. Это указывает на различие в поведении интерфейсов, но не устанавливает конкретную причину отказа мобильного запроса.

Позже запрос Rust с параметрами начальной операции, взятыми из действующей браузерной страницы, вернул страницу с фотографиями и `has_next_page`. Однако самостоятельный HTTP-запрос Rust к `/?variant=following` получил HTML-оболочку без данных предзагрузки, которые присутствовали в DOM после выполнения JavaScript. Поэтому прямой Rust-источник пока не работает; параметры браузерной страницы нельзя считать полученными из сырого ответа. Последующие страницы из Rust также не проверены.

Исходный код [gram: тесты формирования и разбора запроса](https://github.com/LuisUrrutia/gram/blob/318336a44dc2f3adc14186dd1392b8875317fd6f/tests/timeline.test.ts) демонстрирует получение первой страницы из HTML и запросы следующих страниц через GraphQL. [dumpsta-gram: описание операции](https://github.com/stafawashere/dumpsta-gram/blob/6dffc13bbd7d98c4075df25548fb941aa14d1fd7/engine/dumpstagram/_private/web/documents/feed.py) отмечает, что идентификатор запроса может меняться. Оба источника описывают домашнюю выдачу и сами по себе не подтверждают полноту или фильтрацию режима Following.

В [открытом примере параметров домашней выдачи](https://github.com/stafawashere/dumpsta-gram/blob/6dffc13bbd7d98c4075df25548fb941aa14d1fd7/engine/dumpstagram/_private/web/requests/feed.py) три параметра `is_async_ads_*` передаются строкой `"0"`. В неудачном экспериментальном запросе CalmIG использовалась строка `"false"`. Это проверяемое различие, но без нового запроса нельзя считать его причиной четырёх ошибок. Следует также получить идентификатор операции и параметры из текущей страницы, поскольку они могут меняться.

В Linux-сборке подготовлен экспериментальный источник через скрытое окно WebKit: первая страница читается из DOM, последующие запрашиваются внутри той же браузерной сессии. Для следующей страницы используется наблюдавшийся идентификатор операции; при ошибке источник останавливается без повтора. Разбор в `rust-core/src/following_feed.rs` требует подтверждённой подписки на автора, исключает видео, рекламу и неоднозначные элементы. Календарь сохраняет кеш, загружает не более 20 страниц и всегда сообщает о возможной неполноте. WebKit, постраничная обработка и фильтрация проверены на синтетических данных; синхронизация на реальном аккаунте завершилась без ошибки. Полнота выборки за семь дней пока не подтверждена.

Остаётся выяснить, как корректно повторить веб-запрос из Rust-сессии CalmIG, а также сопоставить выборку с вкладкой Following, исключить рекламу, рекомендации, видео и смешанные карусели, проверить порядок и границу семи дней. Полнота выборки не подтверждена; интерфейс должен явно отмечать возможную неполноту. Секреты и содержимое публикаций в этот документ не записывались.

Для следующей проверки можно открыть в Firefox инструменты разработчика → «Сеть», включить сохранение журнала, открыть `https://www.instagram.com/?variant=following` и прокрутить достаточно для подгрузки следующей страницы. Сохранить журнал как HAR в локальный файл и выполнить из корня проекта:

```sh
cargo run --manifest-path rust-core/Cargo.toml --bin inspect-following-har -- /путь/к/network.har
```

Сам HAR содержит чувствительные данные, включая возможные cookie и содержимое публикаций: его нельзя отправлять или добавлять в Git, после проверки его следует удалить. Скрипт читает файл локально и печатает только категории конечных точек, HTTP-статусы, наличие заранее заданных имён полей и признак слова `following` в параметрах; значения, заголовки и тексты ответов он не выводит. Результат не доказывает принадлежность публикаций подпискам или полноту выдачи. Если поле `known_response_keys_found` равно `false`, журнал может не содержать тела ответа или использовать другую структуру. Проверить инструмент на фиктивных данных: `cargo test --manifest-path rust-core/Cargo.toml --bin inspect-following-har`.

Увеличение `count` в запросе списка подписок реализовано и проверено на моках, включая короткие страницы и повторяющийся курсор. Реальный размер страниц и ускорение на аккаунте ещё не измерены; эта оптимизация не устраняет основной масштабируемый по числу аккаунтов обход фотографий.
